# 团队约定（Agent - Human）

> 与本项目开发 Agent 协作时的行为准则。随合作过程持续补充。

## 1. 上下文压力处理

当上下文占用过高时，Agent **不得**擅自采取"紧凑"、"加速"、"一步到位"等牺牲质量的策略。应主动告知人类：

> "当前上下文已占用 X%，下一步需要做 Y，预计需要 Z 轮交互。请指示：继续 / 清理上下文 / 换方向。"

### 已踩的坑

- **Iter-3 Flicker Fix**：Agent 感知上下文紧张，自行压缩代码并一次性修改多个维度（Slot 回调签名 + Host 返回格式 + 删除 tryDiscover + 改转义方式），结果 5 处全炸，排查耗时是直接告知的 3 倍。详见 `iter3-report.md` 4.4 节。

## 2. 差分验证原则

每次只改动一个维度，改动后立即用最小可观测手段验证（探针 / 桩代码 / 最简测试包），通过后再改下一个。

**不做的代价**：Iter-3 改了 5 处 → 输出空白 → 无法定位哪个改动引起 → 逐项回退排查。

## 3. 工作代码保护

正常工作的功能不可因"精简"、"紧凑"、"看起来不必要"等理由直接删除。如需删除，逐项删 → 验证 → 再删下一项。

**反例**：Iter-3 为压缩代码长度删除 `tryDiscover()` 工作区发现函数，导致 `fs` 沙箱读取失败、面板持续空白。

## 4. 参考代码的使用

PoC（Proof of Concept）代码验证了技术可行性，但正式版应比 PoC 更全面。**偏离 PoC 模式时先打桩验证新模式的可用性**，而非直接全线替换。

## 5. 环境边界探索

遇到未文档化的环境约束（JSON 参数长度、转义层级、沙箱权限规则等），先用探针探测建立基线，再写正式代码。避免反复试错。

## 6. 迭代设计确认（先确认，再开发）

**适用范围**：每个迭代（含子迭代）在启动开发前。

**约束**：Agent 必须先向用户提交该迭代的**设计实现方案**（交付范围 / 技术选型 / 验证标准），**经用户确认无误后才能开始写代码**；未确认不得开写。

**流程**：
1. 先产出可评审的迭代设计（含交付件、选型、验收标准）；
2. 提请用户确认；
3. 确认无误 → 启动开发；有异议 → 先修订设计再确认。

**不做**：直接按"看起来合理"就开写，尤其当设计存在多个可选项（如状态机、命名、边界/异常处理）时，必须先让用户拍板。

**理由**：本项目的绑定模型 / 运行状态机 / 归档命名等设计在开发前经历多轮逐条确认，避免了返工与联调成本；先确认设计可显著降低返工率。
