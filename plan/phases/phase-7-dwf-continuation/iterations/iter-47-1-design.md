# Iter-47-1 · 人工介入机制（执行中询问 + 门禁耗尽人工处置）设计方案

> **阶段**：7 / G1（Iter-47 前置机制迭代，用户拍板 2026-10-04 插入）｜ **版本**：host **0.30.0**（本迭代起 0.30.x 线）
> **状态**：待用户确认

---

## 0. 需求（用户定义）

1. **执行中询问**：需求澄清执行过程中，5W2H 关键内容无法从 PRD.md 或知识库获取时，Agent 向人提问——给出**可能性最高的 4 个选项**，由人选择或给出自己的答案。
2. **门禁耗尽人工处置**：门禁检查达到指定重复次数后，主 Session 提示用户工作流失败停止；人可以——检查并**修改交付件后继续** / **审批继续执行**（放行）/ **真正停止**。

## 1. 需求 1：执行中询问——先查证后定路径

**技术前提查证（本迭代第一项）**：任务子会话（subagent spawn）是否具备 ask_user_question 交互能力（工具是否装配到子会话、问题是否能冒泡到 GUI）。真机实验：派发一个带「向用户提问」指令的最小任务，观察行为。

**路径 A（子会话可提问）**——同步澄清：
- skill 文案定义**询问策略**：仅当 5W2H **关键要素**缺失且推理置信度低时提问；每次提问给 4 个选项（按可能性排序）+ 允许自答；
- 溯源分级扩展第三级：**「人工澄清」**（与 直接 / 暂定-推理 / 暂定-假设 并列）——人工答复内容视为需求事实；
- 人工澄清项同样登记知识需求清单（产生方式=人工澄清，所需知识栏记录「已由人工确认，无需补充」或仍需固化为知识库条目的建议）。

**路径 B（子会话不可提问）**——异步澄清（工作流模式更自然）：
- 任务子会话对缺失内容：写暂定描述 + 把澄清问题（4 选项形态）写入交付件「待人工澄清」节；
- 门禁见到该节 → 判 FAIL（理由：存在待人工澄清项）→ 走需求 2 的人工处置通道（人答复 → 修改交付件 → retry，答案由人写入后溯源升「人工澄清」）。

> 两路径对交付件格式的影响一致（溯源分级 + 待澄清形态），仅交互时机不同；查证后择一，skill 按择定路径编写。

## 2. 需求 2：门禁耗尽人工处置（引擎机制，主体工作）

### 2.1 现状与差距

现状：gate `on-failure: retry` + `max-retries: N` 耗尽 → 任务 FAILED → 实例 FAILED 停链（终局，无人工介入点）。

### 2.2 目标状态机（gate-exhausted 分支）

```
门禁 retry 耗尽
  → 任务 FAILED + gateResult=FAIL（保留 gateNote 与末次检查报告路径）
  → 实例 stage=FAILED + stopReason='gate-exhausted'（新值，区别于其它失败）
  → 主会话注入提示（不阻塞注入通道，fire-and-forget）：
    「工作流失败停止：任务 <id> 的门禁 <N> 次未通过（检查报告: <路径>）。
     人工处置三选一：① 检查并修改交付件后对我说"继续"（重跑该任务）
                    ② 对我说"放行 <任务id>"（跳过门禁继续下游）
                    ③ 对我说"停止"（确认终止，实例保持 FAILED）」
```

### 2.3 人工操作通道（编排 agent 会话内自然语言 → workflow 工具）

| 操作 | 用户话术 | 引擎动作 | 实现 |
|---|---|---|---|
| 改后继续 | 「继续」 | FAILED(gate-exhausted) 实例允许 **resume**：该任务回 PENDING（含门禁计数清零），恢复编排 | `workflow_resume`/`/wf/resume` 扩展：gate-exhausted 状态可恢复（其它 FAILED 仍不可） |
| 审批放行 | 「放行 <任务id>」 | 该任务标 DONE、`gateResult='WAIVED'`、`gateNote='人工放行 <时间>'`，下游放行，实例恢复编排 | 新操作 `approveGate(instanceId, taskId)`：engine + `workflow_approve_gate` 工具 + `/wf/approve-gate` 路由 |
| 真停止 | 「停止」 | 确认终局（现 FAILED 保持，active=false） | 现有 stop 语义微调（FAILED 实例可显式关闭 active） |

- 面板：FAILED(gate-exhausted) 态面板显示停止原因与提示文案（注入消息在会话流可见；**本轮不加新按钮**——人工处置以主 Session 对话为入口，符合用户定义；面板快捷按钮记 backlog 视使用体验再定）。
- `workflow_status` 返回值扩展：FAILED 时带 `stopReason`/`failedTaskId`/`gateReportPath`，编排 agent 可据此向用户复述处置选项。

### 2.4 边界与约束

- 放行仅对 **FAILED(gate-exhausted) 的那个任务**有效（不能放行任意任务）；
- resume 后门禁计数从零开始（人已介入，重新计 retries 合理）；
- 多任务并发场景 gate-exhausted 一次只涉及一个任务（串行链/组内第一个耗尽者）；组内其它任务若同时失败按现有 on-failure 语义处理；
- 注入提示只发一次（防重复打扰）；实例重跑后再次耗尽再发。

## 3. 交付与验收

**交付**：
1. 引擎：gate-exhausted 分支 + resume 扩展 + approveGate 操作 + 注入提示；
2. 工具/路由：`workflow_approve_gate` + `/wf/approve-gate` + `workflow_status` 扩展字段；
3. 子会话 ask 能力查证报告（路径 A/B 择定结论 + 实证记录）；
4. 单测：耗尽→状态/元数据/注入；resume 重跑计数清零；放行标记与下游放行；非 gate-exhausted 的 FAILED 拒绝 resume/放行。

**验收（真机）**：构造 `never-pass` 门禁（max-retries:1）工作流 → 耗尽 → 主会话收到三选一提示 → ①改交付件（文件内容改好）后「继续」→ 任务重跑 PASS 过门禁 → COMPLETED；②重放一轮到耗尽 → 「放行」→ WAIVED 继续 → COMPLETED；③「停止」→ 终局。

**版本**：host 0.30.0 起（引擎改动 + 工具 + 文档）。
