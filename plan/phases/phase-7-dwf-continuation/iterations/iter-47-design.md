## 1. 活动定位（用户定义）

需求澄清的目的：**将产品定义文件 PRD.md 转换为系统设计开发所需的初始需求（IR）**。方法是运用 **5W2H**（what / why / who / when / where / how / how-many-much）对 PRD 中各类需求做准确、结构化描述；PRD 未写清之处，通过澄清补充（暂定描述并标记），最终形成标准交付件。

## 3. 执行 skill 设计（sys-req-clarify v0.3）

**任务目标**：运用 5W2H 方法论将 PRD.md 转换为初始需求描述文件（IR 文档），同时输出知识需求清单。

**执行步骤**：
1. **输入定位**：读 `output/00-design-init.md`「输入件检查（PRD）」节确认 PRD 路径与功能点清单；读 PRD 全文。
2. **需求提取**：从 PRD 提取全部需求并分类（业务功能 / 非功能 / 约束与里程碑 / 角色与场景…），逐条建 IR（编号 IR-01…，名称 + 一句话简述）。
3. **5W2H 结构化描述**：每个 IR 按 5W2H 七要素准确描述。**数据来源分级**：
   - PRD 明确 → 直接描述（注明出处章节）；
   - PRD 缺失/含糊 → 澄清补充：给出**暂定描述**（标记「暂定-推理」或「暂定-假设」），并登记到知识需求清单（§3.2）。
   - <!-- 知识库访问锚点：待业务知识补充后，此处增加「检索 knowledge-base/ 相关条目并引用」步骤 -->
4. **术语表**：PRD 业务领域术语（术语 / 定义 / PRD 出处），支撑 IR 描述的一致用词。
5. **汇总与覆盖对账**：IR 汇总表（编号/名称/类别/5W2H 完整度/暂定项数）；与 00 报告功能点清单**逐点对账**（每个功能点 → 对应 IR 编号；新增/拆分/无对应均显式说明）。
6. **知识需求清单**：凡非直接来自 PRD 的推理/假设内容，逐条记录（§3.2 格式）。
7. **输出**：初始需求描述文件 + 知识需求清单，写入任务 outputs 指定路径。

### 3.1 初始需求描述文件模板（templates/req-clarify.md）

```
# 初始需求描述（IR）——<产品名>（<版本>）
## 1 项目需求整体描述        # 产品定位/目标/范围/主要干系人（源自 PRD 概述）
## 2 初始需求详述
### IR-01 <名称>
- 简述：<一句话>
- What（是什么） / Why（为什么需要/价值） / Who（干系人/角色） / When（时机/频次/时效） /
  Where（场景/位置/部署） / How（如何实现的要求/流程约束） / How-many-much（量/度：规模/性能/容量/成本）
- 溯源：PRD <章节>［直接｜暂定-推理｜暂定-假设］
（每个 IR 重复本结构）
## 3 术语表                  # 术语/定义/PRD 出处
## 4 IR 汇总表               # 编号/名称/类别/溯源分级/暂定项数 + 功能点覆盖对账表
## 5 附录（视情况）          # 补充说明：暂定项汇总、待答复问题、引用材料
```

## 4. 门禁 skill 设计（gate-req-clarify v0.3）

**检查原则**：检查对象 = 初始需求描述文件 + 知识需求清单 + PRD 原文（**现场重读 PRD 交叉核对**，不信任任何中间产物）；**输出结构化检查报告**（用户定义：作为 retry 执行任务的改进输入——路径遵循 host 派发指定）。

**检查项**：
1. **格式正确性**：模板结构齐（五章节）；每个 IR 含名称/简述/5W2H 七要素/溯源分级。
2. **完整性（覆盖性，核心）**：与 PRD 对比——PRD 中每个功能/需求点在 IR 汇总表有对应（或显式说明新增/拆分）；**遗漏任何 PRD 需求点即 FAIL**。
3. **一致性**：术语表与 IR 详述用词一致；汇总表与详述一一对应（编号/名称/暂定计数相符）。
4. **正确性（抽查）**：抽 ≥3 个 IR 核对其 5W2H 内容与 PRD 原文相符；标记「直接」的条目其溯源章节真实存在且内容吻合；**凡未标记的推理/假设内容 = FAIL**（知识需求清单登记不全）。
5. 知识需求清单存在非空，且每条能对应到 IR 中的暂定标记。

**判定与输出**：全部通过 → `PASS`；任一不通过 → `FAIL`。两种判定均输出**检查报告**（逐项结果 / 问题清单（指认到 IR 编号与章节）/ 改进建议）到 host 指定路径；FAIL 报告即为 retry 轮执行 skill 的改进输入。

## 5. 真实执行与验收

1. 仓库资产（5 项交付）→ 同步 `sysdesign-trial/` 现场；
2. 真实执行 design-init → req-clarify（两任务后收敛观察）；
3. **验收标准**（人工评审 + 门禁）：
   - IR 文档：PRD 需求**全覆盖**（对账表闭环）、5W2H 描述质量、暂定标记规范；
   - 知识需求清单非空且条目合理（占位 PRD 也必有推理/假设项——如性能数值、部署细节）；
   - 门禁 PASS；**负例**：构造「漏一个 PRD 需求点 + 一个 IR 缺 When 要素 + 一处未标记假设」的坏输出 → 门禁 FAIL 且报告逐条指认；
   - 门禁检查报告落盘且结构符合 §4；
4. host 版本线 0.30.0（本轮 host 代码预计零改动）；
5. 过程问题记 findings（G1 使命：prompt 构造/参数传递/中断继续）。

## 6. 与 v1 设计的差异说明

| v1（作废） | v2（本稿） |
|---|---|
| 以澄清行为为中心（歧义四分类/澄清问题/工作假设为交付主体） | 以 **PRD→IR 转换交付**为中心（IR 详述 + 汇总 + 覆盖对账为交付主体） |
| 门禁不写结论文件（O-7 修正方向试点） | 门禁**输出结构化检查报告**（用户定义：retry 改进输入）——O-7 的真问题是报告的路径/语义/被误用，而非报告本身 |
| 方法论独立成 knowledge 文件 | 5W2H 方法内化于 skill；knowledge 留给**业务知识**（知识库驱动机制：知识需求清单） |
| 单交付件 | 双交付件（IR 文档 + 知识需求清单）+ yaml outputs 修订 |
